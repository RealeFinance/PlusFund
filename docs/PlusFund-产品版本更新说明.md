# PlusFund 产品版本更新说明

适用读者：产品、运营、合作方与 Token 用户

版本范围：2.1.0–2.1.5

本文用业务语言说明 PlusFund 合约版本中的主要变化。2.1.x 主要更新申购赎回流程保护、操作安全和部署治理。各 Token 是否已使用某个版本，应以该 Token 代理当前指向的 implementation 为准；implementation 已发布不代表所有 Token 都已完成升级。

## 版本概览

2.1.0 — PlusFund 新版本系列的基础。为产品提供统一的 Token、申购赎回和运营管理能力。

2.1.1 — 加强链上赎回处理保护。防止同一笔链上赎回被重复销毁 Token。

2.1.2 — 明确区分链上与线下申购赎回。减少记录被送入错误处理流程的风险。

2.1.3 — 统一业务管理员的查询名称并保留原有权限身份。不重置已有授权；使用旧查询接口的运营系统需要适配。

2.1.4 — 加强资金账户配置、跨链来源 ID 和零额转账处理；赎回服务费停止拆分收取，申购服务费配置继续保留。升级前需核实账户配置并处理待完成订单。

2.1.5 — 拒绝零份额申购，避免待处理线下申购订单重复使用 `offChainId`；订单完成后可复用该 ID。升级前需确认没有待处理线下订单。

## 各版本更新

### 2.1.0：PlusFund 新版本系列的基础

2.1.0 建立了 PlusFund Wallet 主线的新合约基础，支持 Token 余额及其来源记录，并为链上和线下的申购赎回业务提供统一的处理框架。

对用户：这是合约能力的基础版本。本身不代表某个具体产品一定提供所有业务渠道；可用渠道仍由产品运营配置决定。

#### 2.1.0 之后的基础交易调整

2.1.1 之前的一次基础调整移除了统一的 0.01 stoken 最低值检查，避免该通用门槛阻挡小额 Token 操作。产品仍可设置自己的最低申购金额和最低赎回 Token 数量，因此具体业务金额仍可能受产品规则限制。

### 2.1.1：保护链上赎回，避免重复销毁

链上赎回在发起时已经销毁相应的 PlusFund Token。此版本加强了赎回记录的来源识别，避免运营后续补充赎回信息时，同一笔记录又被当作线下赎回再次销毁。

对用户：加强链上赎回记录的处理保护。正常赎回业务流程和产品规则不因此改变。

对运营：链上赎回应走链上记录的后续处理流程；不要再对同一记录执行线下销毁操作。

### 2.1.2：隔离链上和线下业务流程

合约为申购和赎回记录明确保存业务渠道，并在后续处理时核对渠道是否匹配。例如，链上申购不能进入线下发放流程，线下赎回也不能进入链上结算流程。

对用户：减少因业务记录进入错误渠道而导致的处理失败或状态不一致。

对运营：处理记录前须确认其创建渠道，并使用对应的完成步骤。升级前还需检查尚未完成的历史记录，因为旧记录不会自动补上新的渠道标记。

### 2.1.3：管理员标识更新，现有授权保持

版本号更新为 2.1.3，并将业务管理员查询名称从 STOKEN_ADMIN 统一为 PLUSFUND_ADMIN。底层权限编号保持不变，因此已有被授权地址不需要重新授权。

对用户：不改变 Token 余额、申购赎回规则或原有管理员授权。

对运营和系统集成：如果部署工具或外部系统通过旧的 STOKEN_ADMIN() 查询管理员地址，需要改用 PLUSFUND_ADMIN()。仍调用旧查询名称的集成可能无法正常读取管理员配置。

### 2.1.4：加强资金账户和转账边界

新部署的资金账户初始为空，申购、链上赎回和赎回款领取会在账户未配置或指向代理自身时停止。部署脚本会读回核对资产接收方、付款方和服务费接收方。跨链导入拒绝零来源 ID；零金额 ERC20 转账则成功返回并发出标准事件，不改变来源队列。

当前业务已取消赎回服务费拆分，赎回时款项全额支付给用户；申购服务费及其多签地址配置保持不变。工厂的 `blacklistAdmin` 配置改为授予完整的 `PLUSFUND_ADMIN` 权限。升级前需确认每个代理没有待处理申购或赎回订单，并检查资金账户和角色配置。版本升级细节见 [2.1.3 → 2.1.4 升级说明](UPGRADE/UPGRADE-v2.1.3-to-v2.1.4.md)。

### 2.1.5：保护申购份额和线下订单编号

零份额的线下申购和链上申购报价会被拒绝，避免用户完成支付后领取不到份额。线下申购和赎回创建时，同类型的待处理订单不能重复使用 `offChainId`；申购执行或赎回销毁完成后，该编号可以再次使用。升级不会迁移旧订单编号，因此升级前须人工确认没有待处理线下申购或赎回。实现还追加了两个存储映射，已通过本地 UUPS 存储布局校验。版本升级细节见 [2.1.4 → 2.1.5 升级说明](UPGRADE/UPGRADE-v2.1.4-to-v2.1.5.md)。

## 部署和升级说明

这一版本周期也补充了统一部署工具，可按产品部署代理合约和独立的 Timelock，并在部署时检查关键实现和治理配置。这些是产品部署与运维能力的改进，不会自动改变已经部署的 Token。

已部署 Token 需要按各自的治理流程单独升级。升级前应检查代理当前版本、管理员和 Timelock 权限，以及尚未完成的申购赎回记录。升级后应记录代理当前 implementation 地址，才能确认该 Token 实际运行的代码版本。
