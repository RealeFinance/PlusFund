## 详细问题

### [代码已整改，定向测试通过；逐代理核验待完成] PF-01 — High：默认自托管配置无法正常支付赎回款

**问题与影响**  
`initialize()` 将 `assetRecipient`、`assetSender` 和 `serviceFeeRecipient` 初始化为代理自身。申购款可由 `onChainSubscribe()` 转入 `assetRecipient`，赎回付款则在 `claimUSD()` 中通过 `safeTransferFrom(assetSender, ...)` 完成。若 `assetSender == address(this)`，标准 ERC20 仍要求相应 allowance；报告指出合约没有为自身付款授权的流程，也没有可提走误入代理资产的正常业务入口。用户先前已在 `onChainRedemption()` 烧掉的份额不会因领取回退而恢复。

**适用条件**  
直接部署后沿用默认值，或部署配置将代理设为资产发送/接收方。若生产实例使用外部 treasury，仍需逐实例核对余额、allowance 和端到端付款链路。

**建议处理**

- 明确支持自托管还是强制外部 treasury。
- 支持自托管时，按自托管路径使用 `safeTransfer`；限制外部 treasury 时，在开放申购前验证并拒绝不合规配置。
- 验证完整流程：申购实际到账、铸造份额、赎回销毁、用户实际收到款项。
- 建立逐代理配置清单，核对 `assetRecipient`、`assetSender`、余额和授权。

**当前整改**  
新部署的 `initialize()` 将 `assetRecipient`、`assetSender`、`serviceFeeRecipient` 设为零地址。`onChainSubscribe()`、`onChainRedemption()` 和 `claimUSD()` 在继续执行前统一检查三个账户均已配置，且均非零、非代理自身；因此未配置时不会接收申购款或先销毁赎回份额。管理员 setter 仍拒绝零地址，并额外拒绝将代理自身设为任一资金账户。该限制不尝试从链上判断一个外部地址是否为 Safe/多签；应由部署配置指定经过批准的外部多签地址，并通过部署后链上读回与预期值逐项比对。工厂部署脚本及直接部署脚本现都执行该读回检查。已部署代理不会重新执行 `initialize()`；升级后若旧值为代理自身，入口检查会阻止相关操作，须先由管理员设置外部账户。

### [方案已定，升级前人工确认待执行] PF-02 — High：旧版未完成订单升级后可能无法处理

**问题与影响**  
2.1.1/2.1.2 为申购和赎回结构增加 `isOnChain`。升级不会自动为旧存储中的记录回填该字段，旧记录默认为 `false`。报告指出历史链上赎回可能已烧份额并写入 token transfer details，但新版 `claimUSD()` 要求 `isOnChain == true`，而再次 burn 又会因已有记录失败；历史链上申购也可能无法进入新版 overwrite/claim 路径。

**适用条件**  
仅影响从旧实现升级、且升级边界存在未完成历史订单的代理。全新部署没有这类旧记录迁移问题。

**建议处理**

- 升级前冻结新订单，由运营人员人工确认申购和赎回均无待处理订单，并记录确认依据。
- 先结清所有在途记录，或实现经过治理授权的 legacy migration/回填机制。
- 使用真实旧实现、旧存储布局和代表性在途订单执行 old-to-new UUPS 升级演练。
- 人工确认仍有待处理订单时，先结清或制定并验证迁移方案，不执行升级。

**当前项目记录**  
`docs/PlusFund-Audit-Remediation-Status-2026-08-24.md` 已记录赎回事件扫描和升级前 `pendingCount == 0` 要求，但没有等价的 pending subscription 扫描。本次处理口径不增加申购扫描工具，改由运营人员在升级前人工确认申购和赎回均无待处理订单，并保留确认依据；这仍不能替代真实旧版升级演练。

### [方案待决策] PF-03 — Medium：provenance dust 可填满接收者队列

**问题与影响**  
公开 `transfer()` 会把来源 lot/token ID 一并写入接收方队列。不同 ID 不能合并；达到 `maxQueueLength` 后，新 ID 入账会回退。报告描述攻击者可向目标地址发送来自不同来源的极小额 lot，填满其默认 100 项队列，阻断新的入账、某些待处理 claim 或跨链 mint。用户可转出 dust 释放空间，但攻击者可能再次填满。单纯提高队列上限还会与单次最多消费 100 个 lot 的限制冲突。

**处理方案判断**  
在保留开放式转账和逐来源 provenance 记录这两项设计约束时，目前没有一种更优的通用方案，能够彻底消除队列填满风险，同时不改变转账权限、来源记录语义或合约复杂度。可选方向都存在取舍，尚无已选定方案；因此当前仍应标记为未整改。

可评估的处理方向：

1. **收款方 opt-in：**未经收款方同意，不接收新的来源 ID；可直接阻止他人用 dust 填队列，但会改变开放转账体验。
2. **设置最小入账量或 dust 清理机制：**减少极小 lot；需避免误删有价值余额或来源记录。
3. **为重要业务预留队列空间：**降低普通转入挤占申购 claim 等业务所需空间的可能；实现和容量管理更复杂。
4. **只提高队列上限：**改动较简单，但不能消除根因；还要与 `MAX_SPEND_SEGMENTS = 100` 的单次消费上限和 gas 成本一并评估。

无论选择哪种方向，都应统一队列容量与单次可消费的最大 lot 数，并覆盖多来源小额转账、队列满、恢复与重复填充场景。

| 审计回复 / 我方处理方式 | 落实动作 | 状态 |
| --- | --- | --- |
| **当前判断：在保留开放转账和逐来源记录的前提下，暂无更优的通用处理方案。** 收款方 opt-in、最小入账量/dust 清理、重要业务容量预留、单纯提高上限都是缓解方向，均需接受相应产品或实现取舍；不能将单纯提高上限视为根因修复。 | 由产品与合约负责人从四个方向中确定可接受的约束变更；统一队列容量与单次消费上限，再实现并覆盖队列满、释放和重复填充场景。 | 方向已列明，尚未决策或实施；问题仍未整改。 |

### [已修复，定向测试通过] PF-04 — Medium：跨链零 ID 可破坏钱包队列边界

**问题与影响**  
报告指出跨链 `mint()` 只验证数组长度和金额总和，没有拒绝 `tokenId == 0`。新钱包的默认 entry ID 也是 0；若零 ID 被导入，内部去重逻辑可能将默认 entry 误认为已存在，从而增加余额却不推进 `tailIndex`。后续消费推进 `headIndex` 后，`tailIndex - headIndex` 可能发生下溢，影响余额枚举和后续入账。

**信任边界**  
该路径由 `POOL_ADMIN_ROLE` 调用；报告未发现普通用户可直接让真实 TokenPool 生成零 ID。因此这是跨链/受信任输入校验问题，不应描述为任意用户可直接铸币。

**当前处理**  
已在 `_addNewTokenDataCrossChain()` 写入 TokenData 或更新钱包队列前拒绝 `td.id == 0`。该校验不改变 `mint()` 函数签名或存储布局；传入零 ID 的调用现在会回退。新增的针对性 Hardhat 回归测试 2/2 通过；真实 TokenPool/message parser 的上游约束仍待核实。

**验证备注**  
当前 `PlusFund` 运行时代码为 24,305 字节，`PlusFundLegacyRoleGetterMock` 为 24,316 字节，均低于 24,576 字节的 EIP-170 限制。PF-01 本次新增拦截使用自定义错误以控制实现体积；自定义错误只扩充 ABI 错误项，不改变既有函数签名。

**建议处理**

- 在任何状态更新前拒绝零 ID、零金额及冲突元数据。
- 在真实 TokenPool/message parser 边界验证输入约束。
- 对 mint/burn 后的 `headIndex <= tailIndex` 和总余额与活动 entries 之和建立不变量测试。

### [工厂已改，定向测试通过；存量实例核验待完成] PF-05 — Medium：工厂配置的 blacklist admin 无法执行拉黑

**问题与影响**  
原 Factory 将 `STOKEN_BLACKLIST_ADMIN_ROLE` 授予 `config.blacklistAdmin`，但 `blacklist()` / `unBlacklist()` 由 `PLUSFUND_ADMIN` 保护。该专用角色只能管理黑名单管理员成员，不能执行实际拉黑或解黑；部署清单因此可能让运营方误以为应急权限已经就绪。

**建议处理**

- **处理口径：由 `PLUSFUND_ADMIN` 执行黑名单操作，不新增专用操作角色。** 工厂现将可选的 `config.blacklistAdmin` 也授予 `PLUSFUND_ADMIN`，与 `config.stokenAdmin` 的权限一致。
- `PLUSFUND_ADMIN` 是宽权限业务管理员，不是黑名单专属权限；配置 `blacklistAdmin` 时，该地址也获得该角色保护的其他管理权限。
- 测试应以配置的 blacklist admin 地址实际调用 `blacklist()` 和 `unBlacklist()`，而不只断言 `hasRole()`。
- 该修改只影响按新工厂代码部署的产品。已部署的工厂合约不会因源码更新而改变；存量代理需核对当前 `PLUSFUND_ADMIN` 持有人，必要时由代理 `DEFAULT_ADMIN_ROLE` 持有人通过 Timelock 授权。
- 逐代理核对真实权限持有人与合规应急流程。

| 审计回复 / 我方处理方式 | 落实动作 | 状态 |
| --- | --- | --- |
| **处理口径：由 `PLUSFUND_ADMIN` 统一管理业务操作与黑名单，不额外引入黑名单操作角色。** | 工厂已将 `blacklistAdmin` 配置地址改为授予 `PLUSFUND_ADMIN`；Runbook 已说明该字段会赋予完整业务管理员权限。工厂测试实际调用拉黑与解黑。 | 工厂和文档已改；Factory 定向测试 9/9 通过。新工厂部署及存量代理角色核验待执行。 |

### [配置已迁至 `.env`；历史 key 有效性待确认] PF-06 — Medium：仓库追踪 provider/explorer 访问值

**问题与影响**  
报告称 `hardhat.config.js` 含有活动配置和注释遗留的硬编码 provider/explorer 访问值。项目方说明目前使用的都是公开 dRPC endpoint；若某个 URL 是无需认证的公共 endpoint，它本身不属于凭证泄露。dRPC 文档同时区分公共 endpoint 与账户专属 endpoint，后者可能把 key 放在 URL 中，并允许按 key 设置额度/停用。

**当前处理与核对**  
项目方说明使用公开 dRPC endpoint；但被跟踪的 `hardhat.config.js` 还含有其他 RPC Provider URL 和非空 Explorer `apiKey` 配置。活动 RPC/Explorer 值现已迁至根目录被 `.gitignore` 忽略的 `.env`；`hardhat.config.js` 仅保留环境变量引用，并新增不含实际值的 `.env.example`。注释中的旧 key 字面值已清理。静态检查不能确认原值是否为有效账户凭证；且迁出当前文件不会清除 Git 历史中的旧内容。本文不抄录这些值。审计报告未发现基金签名私钥。

## 其他信任边界与架构风险

以下是报告列出的重要业务/信任边界，不应与 9 个编号发现重复计数：

- **先烧份额、后由 treasury 付款：**`onChainRedemption()` 会先销毁份额，管理员之后才写入价格/金额，用户再领取。没有取消、超时或链上 NAV 约束；用户承担 treasury/运营延迟风险。
- **申赎金额由管理员决定：**链上没有将申购/赎回金额与 `shares × price` 绑定；获授权管理员输错或密钥被攻破可能导致错发。建议评估宽松 sanity band 和双人审批。
- **Pool 权限较大：**`POOL_ADMIN_ROLE` 可无 allowance mint/burn。工厂白名单只保护初次授权，后续治理仍可授予角色；还需核查 TokenPool 限额、重放保护和治理流程。
- **2.1.3 getter 兼容性：**`STOKEN_ADMIN()` 更名为 `PLUSFUND_ADMIN()`，角色 ID 保持不变，既有角色授权不会因此丢失；仍调用旧 getter 的工厂或运营系统可能调用失败。
- **非标准代币：**申购按实际余额差记账，但报告提示实际到账可能低于名义金额或触发异常代币语义；支持 fee-on-transfer、rebasing、callback token 前应单独制定准入策略并测试。
- **队列与消费上限：**管理员可把队列上限设为 100 以上，但单次消费最多处理 100 个 lot；高度碎片化的转账或赎回可能回退，通常可分批恢复。
